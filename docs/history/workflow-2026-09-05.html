What exists, and what must exist

The target protects settlement from forged or altered transaction records when an attacker controls the primary transaction database. These diagrams distinguish the locally exercised implementation, its recorded evidence and limitations, and the additional infrastructure required for production.

VIEW 2 · FULL PRODUCTION TARGET — INFRASTRUCTURE NOT DEPLOYED

Protect the decision to move value outside the compromised DB

The attacker may insert, edit, delete or reorder primary rows and disable its triggers. The business application, integrity service, independent audit domain and protected settlement domain remain trusted. The local code models these roles. Production additionally requires independently administered accounts/IAM, non-exportable KMS/HSM keys, protected retention and recovery controls; none of that external infrastructure is deployed here.

Steps 1–3 · establish evidence before returning the MAC

The application owns business permissions, assigns the operation UUID and submits the canonical envelope. Service authentication restricts MAC issuance to this trusted caller. A primary-DB credential grants no key-service permissions.

The integrity service commits a durable issuance receipt in the independent audit store before returning the MAC. The receipt binds operation identity/version, exact content hash, schema version and key identifier.

Issuance and the primary insert are separate commits. A missing row is an anomaly requiring reconciliation; it may reflect failure, delay or deletion. The local code uses idempotent retries and quarantines missing issued rows after a short grace interval. Authenticated cancellation/expiry and production recovery procedures remain extensions; they must not silently erase the evidence.

Steps 4–6 · verify content and independent evidence

Primary outbox events, polling or a broker can deliver candidates. These are delivery hints, not authority. Independent issuance reconciliation detects missing work even when primary triggers or events have been removed.

The verifier checks the envelope, schema/key policy, HMAC and independent content hash. It can request VerifyMac, but cannot request issuance or read key material. Verification evidence binds the exact operation version/hash.

Invalid operations enter quarantine; unavailable verification queues work without settlement. No flag written in the primary DB can bypass the decision.

Steps 7–8 · execute the exact checked snapshot once

The processor reads one current snapshot, recomputes its canonical hash and compares it with independent verified evidence. It processes that same immutable in-memory snapshot, without re-reading unchecked amount or recipient fields after the comparison.

The protected settlement DB owns authoritative balances/holds and atomically commits balanced postings, an execution journal, idempotency state and an outcome outbox. Unique constraints and concurrency controls prevent replay and overspending.

A later primary-row change cannot alter the checked snapshot. The primary DB administrator cannot edit protected postings, balances, holds or execution state.

Step 9 · publish outcomes and reconcile after failures

The durable outcome outbox retries delivery to independent audit evidence and primary status projections. Consumers deduplicate events. The protected journal decides whether settlement happened.

No distributed ACID transaction across stores is assumed. Reconciliation resolves delayed evidence and status after a crash without executing the transfer twice. The completion benchmark includes durable outcome evidence.

Funding, correction and reversal use the protected operation path. Original records remain intact; correction/reversal references are included in the HMAC-covered envelope.

Canonical contract: a versioned, byte-exact format binds domain/ledger, operation UUID/version/type, account identifiers, integer amount/currency, precise UTC time, correction references and key identifier. Explicit type/null tags distinguish null from empty values; missing or unknown fields are rejected under the current schema. Golden test vectors define the bytes and expected MACs.
LOCAL HISTORY CODE + PRODUCTION RETENTION TARGET

A history proof needs an independently retained reference

Per-record HMAC detects changes to covered fields. Deletion, truncation and rollback also require a known inventory/order and a protected reference to expected history. A Merkle root stored only beside the data can be rolled back with it.

HMAC supports internal integrity control. Ed25519-signed checkpoints allow public-key verification of the recorded history. Local code checks signatures, provides inclusion proofs and compares retained heads with audit prefixes. A full external verifier additionally needs a consistency protocol and freshness policy against independently retained heads; these are not claimed implemented. Merkle trees still require ordered appends; they do not establish independent observation by themselves.

Production can add independent witnesses and trusted timestamps. Unwitnessed events after the latest external checkpoint remain an explicit exposure window. A signature alone does not establish truthful business input or detect every conflicting history issued by a compromised signing authority.

WORM retention, backups/PITR and tested restores address evidence retention and destruction recovery. They complement cryptographic integrity checks and require production infrastructure and operating procedures.
